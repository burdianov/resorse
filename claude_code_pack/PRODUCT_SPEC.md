# PRODUCT SPECIFICATION — Manpower Deployment & Cost Forecasting

## 1. Product boundaries and terminology
Single UAE construction company delivering data-centre projects; one legal entity and currency AED. Disciplines: Electrical, Mechanical, Plumbing, CSI, MEP, ELV, General. Departments are classified Head Office or Site; each designation belongs to one department and one discipline. Employees have a single `full_name`, employee code/ID, designation, status and relevant master data. Projects include project code, name, tender/awarded lifecycle, start, contractual completion and independently editable forecast completion dates. Head Office is an allocation/cost centre, not merely a UI label.

**Three user journeys:** (1) anonymous-position tender forecasts, (2) awarded-project named/unnamed resource forecasts plus actual employee movement records, (3) read-only cross-project capacity and cost consolidation, with project inclusion/exclusion and no tender/awarded double counting.

## 2. Foundation requirements (Stage A)
Build the reusable platform first, with no construction domain tables/routes. Adapt QTC360-like UI geometry: 64px top bar, 260px expanded / 64px collapsed sidebar, 24px main padding, subtle blue accent and neutral light/dark surfaces, keyboard command palette, responsive mobile drawer, real notifications and role-filtered navigation. Maintain 29 source-inspired UI primitives; reusable DataTable with sorting, filtering, pagination, column preferences and CSV hooks; RHF/Zod forms; loading/empty/error/403/404/offline states.

Required routes: `/login`, `/change-password`, `/dashboard`, `/notifications`, `/profile`, `/profile/security`, `/admin/users`, `/admin/roles`, `/admin/permissions`, `/admin/settings`, `/admin/audit`, dev-only `/tools/components`, `/403`, `/404`. Generic sample permission-protected user-directory PDF. Private file storage, Gotenberg conversion and PDF preview. Secure auth (prefer PostgreSQL-backed rotating opaque HttpOnly sessions or short access + HttpOnly rotating refresh; document choice), CSRF defense, server RBAC union of multiple roles, audit, settings and preferences. Admin-only account provisioning, forced password change and protected bootstrap. Fresh migrations and real tests. No Redis/Next.js.

## 3. Master data (Stage B)
- `disciplines`: controlled codes and names; seven initial values above, idempotently seeded, with safe administrative editing policy.
- `departments`: name, code, classification (`HEAD_OFFICE` / `SITE`), active flag.
- `designations`: name, code, department ID, discipline ID, active flag. Department and discipline are each single-valued unless explicitly revised.
- `designation_rates`: designation ID, AED/hour Decimal, `effective_from`, optional end-of-validity derived from next row; no overlapping/duplicate effective dates; full history.
- `employees`: `employee_id` unique business identifier, `full_name`, designation ID, active/employment status, optional hire/end dates and contact fields only if justified. Do not split name.
- `employee_rates`: employee ID, AED/hour Decimal, effective date/history; overrides designation rate when effective. Never retroactively rewrite historical records silently.
- `projects`: unique code, name, tender/awarded status, project start, contractual completion, forecast completion, project responsible person, optional discipline metadata. Preserve tender-to-award identity to avoid duplicate demand.
- `cost_centres`: project and Head Office; explicitly typed; no invented legal entities or currencies.
- Users and employees are distinct records, optionally linked for authorized user accounts; don't assume every employee can log in.

## 4. Rates and cost engine
Standard full-month nominal hours = **26 days × 8 hours = 208 hours**. Monthly full allocation at rate R: `208 × R × allocation_pct / 100` AED. Determine rate by the date policy approved in `DECISIONS.md` (do not assume mid-month rate changes can be ignored). For a partial first/last month, calculate a baseline partial-month percentage from eligible working days divided by 26 (with full-month explicitly normalized to 100%); the working-day calendar and caps require confirmation. Store percentages as decimal values with a clear precision/rounding rule; do not use floats for money.

Forecasts are independent snapshots. A position row has a stable UUID, department/designation, optional employee ID (awarded only), start/end dates, month percentage overrides and a display order. The same designation can appear in multiple rows. A tender row must not carry an actual employee ID. Forecast cost is computed from the selected effective hourly rate (employee override if named, otherwise designation), month allocation, and 208 hours. Explicitly test month boundaries, leap years, empty/zero allocation, changes to rates, and forecast revisions.

**Edited-cell retention rule:** when row dates change, keep manually edited month values for months still within the new interval; remove months outside it; initialize newly included months to default 100% or computed partial-month percentage. If an old boundary month remains but its eligible days change, manual overrides stay untouched; non-overridden default values are recalculated. Distinguish default and manually edited cells in persistence.

**Revision rule:** initial saved forecast is Revision 0. Saving normally updates the current working revision according to an explicitly defined draft/published policy; checking `Create new Revision` creates the next immutable numbered snapshot. Only the latest **published** revision feeds consolidation/reports, unless a privileged user explicitly selects history. Define whether edits without a new revision mutate the latest published snapshot before implementing; see decisions.

## 5. Tender planning UX
Tender selector -> site departments -> designations -> duplicate/add rows -> bulk date assignment -> editable monthly matrix. Excel template download, upload preview, validation and atomic import for designation/date rows. Timeline should extend beyond the last resource end date to allow planning (configurable extra months). Sticky position columns and month headers, horizontal virtualization/scroll, row groupings, bulk operations, totals by month/department/discipline, filter/search, keyboard editing, copy/paste and unsaved-change warning. The matrix should show allocation %, AED monthly cost, and resource FTE equivalents without confusing those metrics. Export executive-quality A3 landscape PDF (A4 optional), with project metadata, revision, assumptions, monthly/total costs, grouping, page numbers and print legibility.

## 6. Awarded project planning
On award, maintain project identity and create a new awarded forecast (possibly seeded from latest tender revision via an explicit reviewed conversion). Positions may be named employees or vacant future hires; duplicate designation rows remain supported. Employee and designation/date bulk import and manual editing. Hourly rate precedence: employee-specific effective rate, else designation effective rate. Resource forecasting can be revised; do not silently change manual forecasts because an employee is transferred. Instead flag actual-vs-forecast discrepancies and offer an explicit reconciliation action with preview, approval/audit as appropriate. Show named/vacant demand, forecast cost, rate provenance, conflicts and missing-rate alerts.

## 7. Actual assignments and movements
Actual project-month cost is derived from employee assignment date intervals and applicable rates; **never** from manual forecast percentages. Persist actual costs at project-month aggregate level, not as a separate employee-month actual cost ledger; computation may use per-employee intermediates transiently for accuracy. When an employee remains assigned to the same project without a transfer/reallocation, 100% of their actual cost continues to accrue to that project automatically for each subsequent month; no recurring manual entry.

Every actual assignment has a start date and end date. If the end date is not known when entering a continuing assignment, use an explicitly documented provisional/open-end workflow plus persistent alert until the end date is supplied; never mark a missing end date as complete. The responsible person for the project may maintain the assignment end date; Resource Manager may also manage it. The approval owner for a transfer out is the responsible person of the employee's **actual source project on the effective/request date**, not whoever owns the forecast allocation.

Transfer request: employee, designation, source, destination, proposed effective start/end, reason, requester, approval/rejection history, actual date and status. Resource Manager or requesting project's responsible person may initiate. Validate overlapping assignments, authority, past-date changes, cross-project conflicts, and idempotent approval. Generate a formal PDF for request, approval and final transfer record. A transfer's effective date determines actual cost allocation for that month, not the request creation date. Rejection leaves assignments unchanged.

**Shared staff recommendation (requires sign-off):** support multiple concurrent actual assignment slices with effective dates and percentage shares summing to 100% across project(s)/Head Office on each day. Allocate monthly actual cost by effective date × share × hourly rate. Do not reuse forecast percentages as actual shares. Use a dedicated approved shared-assignment record, not overlapping full-time transfers. Ensure no >100% daily assignment, and define gaps/unassigned treatment.

Leave: employee, leave type, inclusive start/end, approval/status if adopted, and current assignments preserved. Confirmed rule: paid leave cost remains charged to existing assigned project(s) for the first month and is split by the existing allocation. Rules for leave beyond first month and unpaid leave need approval. Day/night shift recorded effective-dated if needed; shift premiums are not assumed. Resignation/termination workflow must close or flag assignments, avoid retroactive data loss and update capacity availability. Other recommended event types: hire/onboarding, secondment, temporary Head Office assignment, return from leave, demobilization and correction/reversal with audit.

## 8. Cost reporting and cost-at-completion
Project reporting must use **Actual Cost** terminology (not timesheet-based implied actuals). For a reporting cutoff month, `Cost at Completion = sum(actual project-month costs for closed/current reporting months) + sum(forecast project-month costs for remaining future months)`. At project start, cost-at-completion is entirely forecast; each completed reporting month replaces its forecast portion with actual cost. Define the treatment of the current incomplete month and financial period close in `DECISIONS.md`. Preserve historical monthly actual totals, calculation version/inputs and auditability; prevent unauthorized manual edits. Allow authorized recalculation with visible differences when retroactive assignments/rates change.

## 9. Consolidated resource planning
Read-only planning cockpit across selected tender and awarded projects; if a tender is awarded, include its awarded project representation only. Resource demand by month, designation, department and discipline; supply of active employees by qualification/availability; shortage/excess, named vs vacant demand, upcoming demobilizations, hires needed, double booking/conflicts, forecast vs actual, project and Head Office costs, and cost-at-completion. Filters by status, project, department, discipline, month horizon; saved view optional. Visuals: timeline heatmap, capacity-vs-demand bars, KPI tiles from real data, exception queue, drill-down and exportable executive A3 PDF. Read-only means no hidden inline mutations.

**Planning definition:** one 100% position-month = 1 FTE-month; partial month normalized consistently. Do not count a person as available if their actual/committed assignment consumes their capacity. Vacant forecast positions represent demand, not supply. Tender demand can be scenario-weighted only if explicitly enabled and labeled; never silently treat all unawarded demand as guaranteed workload.

## 10. Security and roles
Multiple roles per user. Suggested role catalog: Super Admin/Admin, Resource Manager, Project Manager, Project Director, Commercial/Estimation, Timekeeper, Viewer/Management. Grant permissions by action plus project scope; role membership alone never authorizes unrelated projects. Distinguish tender edit, awarded forecast edit, actual assignment edit, transfer request, source approval, end-date maintenance, cost/rate view, report export, audit view, master data edit. Rates and employee personal data are sensitive: least privilege. Project Directors can oversee authorized projects; viewers are read-only. All APIs, report queries and file downloads enforce the same scope.

## 11. Operational quality
Real PostgreSQL integration tests; frontend component tests; browser E2E on migrated test DB; A3/A4 PDF validation and visual checks; role/project scope negative tests; Excel import validation; concurrency tests on transfer approvals and revision numbering; CI and Docker release gates. Documentation for setup, migrations, bootstrap, backup/restore, audit, operator tasks and release. No Redis, Next.js, or QTC360-specific domain artifacts.
