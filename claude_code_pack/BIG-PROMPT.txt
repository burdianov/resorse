# 6. IDENTITY, AUTHENTICATION, SESSIONS AND SECURITY

## 6.1 Account lifecycle

Database-backed `User` has UUID, unique normalized email, `full_name` (single field), optional phone, hashed password, `is_active`, `is_deleted`, `is_superuser`, `must_change_password`, `password_reset_at`, `token_version`, created/updated metadata, optional last-login metadata. No domain-specific `designation_id`, `projects` relationship or hard-coded company identifier. Administrators create accounts through `/admin/users` using explicit temporary password or securely generated initial password shown once; never log/echo passwords later. First-login required change. Admin reset increments revocation version and forces change. Password changes require current password except privileged reset. Account deactivation/deletion revokes sessions. Email is canonicalized consistently and unique at DB layer. Disallow last-super-admin removal/deactivation and non-super-admin privilege escalation.

Use contemporary robust password hashing (Argon2id preferred if selection is justified; bcrypt is allowed when properly configured and tested), strong configurable password policy with length/denylist/rate limits where feasible; never store raw password, never return `hashed_password` in API response. Expired temporary password -> clear recovery/admin-reset UX, not a dead-end form. First-login change should not accidentally grant ordinary app access before completion; API should enforce `must_change_password` for all regular endpoints.

## 6.2 Session design — improve upon source

The source uses access and refresh JWTs in `localStorage` and Axios interceptors with one refresh promise. **Do not blindly reproduce this security tradeoff.** Implement secure, production-appropriate authentication without Redis: a short-lived access token (in memory only, or an appropriate secure cookie) and an **HttpOnly, Secure, SameSite** refresh cookie with server-managed rotation/revocation in PostgreSQL. Alternatively use entirely opaque HttpOnly session cookies stored as hashed session IDs in PostgreSQL. Choose one documented design and implement it consistently; favor same-origin reverse proxy `/api/v1` to avoid unnecessary cross-origin cookie complexity.

- Login/logout/refresh/me/change password, status checks, disabled-user and version-based revocation.
- Rotate refresh tokens with hashed token/session rows, absolute expiry, replay/reuse detection, logout-current and logout-all/revoke-all (if supported). No exposed refresh secret in JavaScript or `localStorage`.
- Protect cookie-authenticated state-changing operations with tested SameSite policy and robust CSRF mitigation (origin validation and/or CSRF token as appropriate). Keep CORS tight with no wildcard+credentials, ensure TLS in prod, HTTP-only development handling, secure cookie domain/path.
- Avoid refresh request loops and duplicate refreshes: client `api.ts` performs **single-flight** refresh and retries an original request once, except auth/refresh/login requests. Race-proof across tabs where practical, clear private caches when identity changes.
- Redirect to `/login` only after clear anonymous/expired-auth resolution; **network failure and 5xx get a Retry UI**, as the source auth guard intends. An anonymous visitor to `/dashboard` must be redirected. A logged-in unauthorized user must see 403 without data leak. Persist intended destination safely within the app.
- Login failures must not enumerate users. Rate-limit by IP/account using PostgreSQL-backed counters or other non-Redis strategy with tested concurrency; consider reverse-proxy protections. Record security events with privacy-aware details, not passwords or raw tokens. Support audit of reset/deactivate/logout and security-sensitive admin changes.
- Source's backend has a global FastAPI `APIRouter.include_router` monkey patch for an old compatibility issue in `backend/app/main.py`. **Do not copy this monkey patch**. Use normal current FastAPI router composition and adjust paths properly.

## 6.3 RBAC model and authorization

Model `Role`, `Permission`, `user_roles` (M:N) and `role_permissions` (M:N) with UUIDs, unique `name`/`code`, safe admin CRUD and `role.permissions` associations. User can have **multiple roles**. Permission codes are machine-stable (`users.read`, `users.create`, `users.update`, `users.deactivate`, `users.reset_password`, `roles.read`, `roles.manage`, `permissions.read`, `permissions.manage`, `settings.read`, `settings.manage`, `audit.read`, `notifications.read`, `notifications.manage_own`, `files.read`, `files.create`, `reports.generate`); add granular variants only as needed.

- Default `super_admin`, `admin`, `viewer` roles with narrowly justified capabilities; seeded roles and permissions are idempotent. Super-admin may bootstrap safely. `viewer` is read-only through explicit permission definitions; **do not** use the source shortcut that blocks any user whose role set equals `{viewer}` from even appropriate read operations.
- Server `get_current_user`, `require_permission`, `require_admin` must check active/deleted status and effective permissions every request (or safely invalidated cache), fail closed, and apply filters on SQL queries. Route guard and `PermissionGate`/navigation visibility share permission registry but are never the security boundary.
- Least-privilege protection for role assignment, admin role modification, permission creation, super-admin role update, self-demotion/deletion and simultaneous administrative changes. Validate unknown role/permission IDs and duplicate associations.
- On role changes, invalidate affected users' sessions or ensure next request re-evaluates privileges (source `token_version` supplies a pattern). Prevent a normal admin from granting themselves elevated rights. Audit every permission/role change with before/after sanitized diff.
- Provide a documented future *resource-scope policy interface* (`ScopePolicy`/resource object checks) to extend RBAC to projects/business units, but **do not create** QTC360 project masters or grant client-controlled scope IDs authority. If scope selection is added later, server must always verify membership.

## 6.4 Global security baseline

Validate environment on startup (strong secret, DB connection, TLS/cookie settings, production origins), build properly parameterized DB queries, input schemas, least privilege DB user, standard non-sensitive errors, no leaking call stacks in prod, body/upload caps, filename/path traversal prevention, MIME + magic-byte checking, malware scan hook, safe file response headers, no public uploads volume, CSP for static app, X-Content-Type-Options, Referrer-Policy, HSTS/TLS in production. Avoid debug `print` logs containing users or raw project memberships (present in old source). Use structured logs with request IDs and secrets redaction. CSP must allow Vite static JS and only required API connections. Document threat model including XSS, CSRF, leaked refresh tokens, horizontal privilege escalation, audit tampering, rate limit bypass and malicious CSV/PDF uploads.

```ts
  listAvailable(): Promise<TContext[]>;
  getSelected(): TContext | null;
  select(context: TContext): Promise<void> | void;
}
```

These are illustrative conceptual types, not literal hard constraints. The backend `ScopePolicy` belongs in Python, not the TypeScript frontend; show the corresponding backend interface in architecture docs. Avoid runtime plugin loaders from arbitrary remote code, and make permission codes registered server-side.
